# Marketplace data-analysis agent — demo brief

**5 August 2026** · updated 6 August · every figure traces to the
`ticket-investigations-*.md` logs.

---

## 1. What it is, in four lines

An agent that works marketplace ad-performance tickets. You describe the problem in plain
language; it picks a runbook, pulls data, does the maths, and checks in at each step.

**It never writes SQL.** All 43 reports are reviewed SQL templates frozen in kamService.
The agent only chooses *which columns, which dates, which filters*. It picks from a menu it
cannot alter — so if a number looks wrong, the SQL is reviewable in a PR.

```
plain-language question  →  1 of 11 runbooks  →  MCP  →  kamService  →  BigQuery
```

## 4. Three worth showing in the demo

### Ticket 4 — the advertiser was competing with itself

| Their table said | Reality |
|---|---|
| 4 competitors driving up CPC | All 4 rows were Centrum's own campaigns |
| Competitors outbidding them | Rivals bid ₹11.01–₹15.00. Centrum holds 93.2% of spend |

"centrum" was targeted in **8 Centrum campaigns, 6 created in the week before the ticket.**
In a second-price auction your runner-up sets your price — their runner-up was themselves.
Lowering the bid just loses the slot to a sibling.

### Ticket 14 — one brand broke the whole marketplace metric

| Date | Requests | Responses | RR |
|---|---|---|---|
| Jul 30 | 840,046 | 543,602 | 64.71% |
| **Jul 31** | **1,434,501** | 529,233 | **36.89%** |

Jul 31 added 594,455 requests and **lost** responses. Cause: `Anua` requests went 689 →
633,205 in one day, all unfilled — the brand is in the catalogue but has no campaign, so
nothing can serve. **Excluding Anua, RR that day was 60.70% vs 60.47% the day before.**
Still leaking ~20k requests/day.

### Ticket 15 — the agent reversed itself 7 times and logged every one

The best demonstration of behaviour under pressure. Each reversal came from digging one
level deeper, not from being told it was wrong.

| It first said | Then found |
|---|---|
| CPC rise is an artifact of falling volume | True at page level, but hid a real rise underneath |
| Cause is a category floor raise | Killed by its own evidence — bid distribution had the wrong shape |
| EcoFlow is the best example, CPC +31.7% | For SKUs served on both days CPC **fell 5.3%**. Wrote: *"EcoFlow was a poorly chosen exemplar"* |

**And it said the ticket was the small problem.** The CPC issue was ZAR 5,273/day = **0.57%
of spend**. Meanwhile marketplace CTR was down 8–10% on matched weekdays, affecting **100%
of spend**, with no ticket at all.

## 5. What we learned across all 15

| Pattern | Detail |
|---|---|
| **Read the denominator** | RR fell because requests rose. CTR fell because impressions rose. CPC "rose" because cheap clicks vanished. The numerator was fine every time |
| **But keep decomposing** | Ticket 15 proves "check the denominator" isn't enough — it was right at page level and still wrong. Rule: **decompose until the explanation stops changing** |
| **Match the weekday** | Ticket 15's headline swung from +14.7% to +1.2% purely on baseline choice. Comparing a Tuesday to a weekend invents incidents |
| **Self-competition looks like competitors** | Twice (1, 4). Both advertisers blamed rivals |
| **New-campaign ramp looks like a fault** | Twice (12, 13). Both judged from eyeballing a live search page |
| **Tickets are often wrong** | Wrong agency, wrong ID type, mis-read tables, empty bodies. Trust the data over the ticket |

## 6. Where it says "I can't answer that"

This is the behaviour worth demoing if you only show one thing.

| Situation | What it did |
|---|---|
| Campaign with budget but no spend | Found zero products attached and **stopped**: *"you cannot lose an auction you never entered"* |
| Asked to rank worst keywords | Report caps at 100k rows alphabetically — it could only see 0.9% of requests. **Refused to rank**, answered at category level where data was complete |
| Report returned zero rows | Re-ran against a campaign known to be spending, to prove the report was healthy and the emptiness real |
| Asked for merchant attribution | Largest merchant was 1.1% of 1,729. Said a ranking would be padding — **and didn't build it** |
| A published conclusion was contradicted | Revised it and **struck through** the old figures rather than deleting them |
| User said "you're wrong, check 15 days" | Confirmed the user was right, then found **its own restated version was also wrong** (partial day included) and withdrew that too |

It also caught three defects in our own tooling: a report silently ignoring a filter, a
`daily_budget = 0` that actually meant "no row", and an MCP bug where 1,000 rows carried
only 30.8% of true spend while claiming nothing was dropped.

## 7. What's still missing

### Before production — deployment steps, not config work

| Step | Why |
|---|---|
| Load **173 `perf_*` columns** into production `columnMetadata` | They exist only in test's database today |
| Register `GCP_PERF_BQ_KAM_CREDENTIALS` in production | Every report uses it |
| Merge kamService **#510** first | Adds the visibility enum. The 15 config PRs (#546–#560) follow it |

### Capability gaps

| Gap | Consequence |
|---|---|
| No keyword→category mapping is readable | Tickets 1, 3, 12 all asked. Can only be inferred from which cache served |
| No **category** floor-price report | The one thing non-search CPC tickets need. Existing tool is keyword-scoped |
| No page-scoped ROAS anywhere | "Did the advertisers paying more actually convert?" is unanswerable. Needs one fact table joining merchant × page × revenue |
| No audit trail for bid changes | Status, budget and product changes are logged. Bids are not |
| `bid` / `original_bid` / `raw_bid` undocumented | Not defined in any of the 43 configs. Ticket 15's analysis had to infer it |
| `AUDIT_EVENTS_REPORT` times out past ~4 days | 11-day windows return 504 |
| Attributed metrics keep settling | Same query returned ZAR 11,771,088 then 11,821,990 hours apart. Flagged, not correctable |
| Metric-column filters silently ignored | They become SQL aggregates, so the filter is dropped with no error |

### Data quality we should fix — found by the agent, not agent problems

| Finding | Scale |
|---|---|
| Apollo category requests arrive untagged | **92.2%** |
| TIRA CUSTOM requests have blank `category_l1` | **100%** |
| TIRA unfillable `Anua` requests | ~20k/day, still open |
| Takealot campaign IDs churn weekly | **58%** — breaks any campaign-keyed analysis |
| Takealot product-page clicks at exactly the ZAR 1.50 floor | **57.98%** — little price signal on half the page |
| A relevance cache was retired mid-afternoon, unannounced | Two caches then moved +15–20%, one moved −22%. **Nobody was watching** |
| Apollo taxonomy contains a literal duplicate | "Ear Nose & Oropharynx" vs "Ear, Nose & Oropharynx" |

## 8. The three things I'd tell the team

**1. Every defect came from running it, never from reading it.** 13 defects across 11 runs.
Static checks — valid column names, report types exist, docs in sync — passed cleanly the
whole time and caught **none** of them. Any review of a future runbook has to include
running it.

**2. When a bug appears twice, stop fixing instances and sweep.** The same partition-pruning
bug appeared four times. I found three by accident, then swept and found the fourth.
**~277 GB → ~38 GB** per full pass, identical data.

**3. A near-100% response rate can be a warning, not health.** Three takealot ad units sat
at 99.99% fill, then collapsed. I called it a platform failure and recommended escalation.
**I was wrong** — a house campaign at CPM 1.01 was winning every auction and hit its end
date. ZAR 1,782 of filler was answering 2.4M requests. The 99.99% *was* the signal.

**On readiness, plainly:** the reports are done and reviewed. Against test it works and has
produced 15 usable answers. Production waits on the deployment steps above — I wouldn't
soften that for anyone deciding whether to depend on it.

## 9. Suggested demo run

Six minutes, real anomaly, clean narrative:

```
For agency 105, find a PLA campaign (campaign_type = PERFORMANCE) with budget but low
spend 2026-08-01..02, then diagnose why it isn't spending.
Use only osmos-performance-local.
```

It picks its own subject, uses a control campaign to rule out a false negative, hits a hard
gate, stops, and hands back an answer with a named owner — *"route to onboarding, not
ads-ops bid tuning."*

| Before you run | Why |
|---|---|
| **Restart the session** | The MCP server loads at session start; recent fixes won't be live otherwise |
| Avoid marketplace-wide keyword drills | Slow — calls get backgrounded past the 120-second tool timeout |

| Looks like a failure, isn't | Reason |
|---|---|
| `CAMPAIGN_NETWORKS_REPORT` empty for takealot | That data legitimately lives in other agencies |
| Large fetches return a file path, not rows | By design — the agent analyses the complete set without burning context |
