# KAM report catalogue

The reports behind this plugin's skills. You request **columns** — the SQL is frozen in a
reviewed template, so a caller chooses *which columns, which dates, which filters*, never
*which SQL*.

Served from `/osmosReportingMcp/internalPerformance`.

> Generated by `scripts/build_plugin_knowledge.py` in the `osmos-data-analysis-agent`
> repo. **Do not hand-edit** — regenerate, or it drifts from the deployed configs.

## Calling a report

```
run_report(reportType=<external name>, attributes=[...], metrics=[...],
           dateRanges=[{startDate, endDate}], filters=[...])
```

- You group by whatever attributes you request. **A report declaring 13 attributes is a
  menu, not a 13-column report.**
- Requesting **no** attributes returns the ungrouped total — only for reports marked
  *ungrouped*; the others need at least one.
- **Required filters are enforced by the MCP** (`run_report.py`), and with AND semantics:
  every listed filter must be supplied.
- Comparisons are **two calls**. These reports are single-period and emit no
  `_prev` / `_change` / `_perc` variants.

## Known issues

| Report | Issue | What to do |
|---|---|---|
| `AUDIT_EVENTS_REPORT` | `action_type_id` is INT64 while KAM builds the filter as a string. **Known kamService issue — a fix is in review, expected to deploy in the second half of August 2026.** | until then the selector carries `SAFE_CAST(... AS STRING)`; pass `perf_action_type_id` as a string (`"50"`, not `50`). Once the platform fix lands the cast can come out and this row with it |
| _all reports_ | **metric filters are silently ignored on these 43 reports.** kamService does support them, but only when the query carries the `__METRICS_FILTERS__` placeholder after `__ATTRIBUTES_GROUP_BY__`, which it renders as a `HAVING` clause — 69 configs elsewhere in the repo use it, none of these 43 do. So a `perf_spend > 100000` in `metricsFilters` returns unfiltered rows, with no error. | filter on attributes only; apply metric thresholds yourself after fetching. If a report ever needs it, adding the placeholder is backward-compatible — it renders to an empty string when no `metricsFilters` are passed (verified on `PAGE_PERFORMANCE_PLA_REPORT`: unchanged without, 5 rows → 2 with `perf_spend > 100000`). Note the request field is `metricsFilters`, separate from `filters`, and operators are symbols (`>`, `>=`, `<`), not names |
| `CAMPAIGN_KEYWORDS_REPORT` | `perf_is_negative` cannot be filtered with the `IN` operator — BigQuery rejects it with "No matching signature for operator IN" regardless of whether the value is a string or an int | use `EQUALS` (or `=`); the value type does not matter, both `"0"` and `0` work. `perf_campaign_id` still needs `IN` |
| `CAMPAIGN_LOOKUP_REPORT` | exposed `mcd.effective_status` as `perf_campaign_status` while three other reports call the same column `perf_effective_status` — renamed for consistency | use `perf_effective_status`; there is no `perf_campaign_status` |
| `DAILY_ORDER_TRENDS_REPORT` | `channel` removed — it selected `cvcpf.channel`, unbound in the outer query, and cannot be exposed without inflating the site metrics | no PLA/Display split here; use `MERCHANT_PERFORMANCE_REPORT` |
| `RESPONDED_SKUS_REPORT` | rows are SKU-grain, so impressions/clicks are ~3-4x the ad-level figures (one ad impression shows several SKUs), and `perf_spend` is derived from the clicks mapping's per-click bid — it therefore **understates badly for CPM-billed campaigns**. Measured on bigbasket FF_Snacks 2026-08-03..04: SKU spend INR 1,760 vs billed INR 19,808 | use it for *which SKUs responded*, never for spend or for totals. Take spend and impressions from `INTERNAL_KEYWORD_PERFORMANCE_REPORT` |
| `RESPONDED_SKUS_REPORT` | `page_type` used to be pinned to `'SEARCH'` in two places with no way to see or change it, so 42.8% of responded-SKU impressions were unreachable. **Now fixed** — `perf_page_type` is selectable and filterable. Agency 105, 2026-08-01..02: SEARCH 28,740,964 · PRODUCT 18,130,645 · CATEGORY 1,668,369 · CUSTOM 1,299,506 · HOME 383,798, total 50,223,282. | always pass or group by `perf_page_type` — the report now spans all surfaces, so an unscoped pull mixes them. Filtering to SEARCH reproduces the old pinned totals exactly |
| `RESPONDED_SKUS_REPORT` | declares `perf_keyword` required, but **kamService does not enforce `externalRequiredFilters`** — an unscoped fetch runs and never returns | **always scope by `keyword`**; the MCP applies it, direct callers must too |
| `RESPONDED_SKUS_REPORT` | `perf_campaign_id` renamed to `perf_internal_campaign_id` — it holds the internal id, not the marketing id in the UI | filter with the internal id (from `CAMPAIGN_LOOKUP_REPORT`); the two are not 1:1 |
| `GMV_ATTRIBUTION_REPORT` | `channel` removed — the template is ungrouped (no attributes slot) | request no attributes; it returns one total row |
| `RR_DISPLAY_REPORT` | no `store_id` — the Display facts table lacks the column | use `RR_PLA_REPORT` for store-level RR |
| `CAMPAIGN_LOOKUP_REPORT` · `MERCHANT_LOOKUP_REPORT` | resolve an entity from **any one of** several id keys, so they deliberately declare no required filter | pass whichever id you hold |

## Verification state

All 43 reports were fetched against agency 105 (takealot, ZAR) requesting every exposed
column, and the 15 consolidated reports were diffed row-by-row against the 42 they replaced:
**39/39 runnable pairs identical** — zero rows lost, gained or drifted.

**A report returning no rows is usually the request, not the report.**
`SEARCH_QUERY_MATCH_PERFORMANCE_REPORT` was recorded here as "0 rows" until the cause was
found: the test had paired `perf_os_client_id` with a `perf_campaign_id` that client does not
own. With a matching pair it returns rows normally. Check the filter values before concluding
a report is broken.

Untested: `is_negative` on `CAMPAIGN_KEYWORDS_REPORT` (no test campaign has keywords) and
`attributed_sales` (0.00 on every keyword row in the window).
